## 2. PAGED RESULTS — the core question

ldap3 0.12 offers **two** distinct things both named `PagedResults`. They live in different
modules and serve different layers:

### 2a. The raw RFC 2696 control: `ldap3::controls::PagedResults`

Defined in `src/controls_impl/paged_results.rs:15-22`:

```rust
pub struct PagedResults {
    pub size: i32,      // request: desired page size; response: server estimate
    pub cookie: Vec<u8>,// paging cookie
}
```

- OID constant: `PAGED_RESULTS_OID = "1.2.840.113556.1.4.319"` (`paged_results.rs:24`).
- Re-exported as `ldap3::controls::PagedResults` (`src/lib.rs:209`).
- It is a *request-and-response* control (same struct for both, per `lib.rs:154`).
- Request encode: `impl From<PagedResults> for RawControl` (`paged_results.rs:28-53`) —
  you convert with `.into()`.
- Response decode: `impl ControlParser for PagedResults { fn parse(val:&[u8]) -> PagedResults }`
  (`paged_results.rs:55-83`); used as `raw.parse::<PagedResults>()`.
- `impl MakeCritical for PagedResults {}` (`paged_results.rs:26`) — can be marked critical.

This is the building block for the **manual control loop** (candidate (b)).

### 2b. The Adapter: `ldap3::adapters::PagedResults<S, A>`

Defined in `src/adapters.rs:295-330`:

- Constructor: `adapters::PagedResults::new(page_size: i32)` (`adapters.rs:319`).
  **Note the page size is `i32`, not `usize`.**
- It implements `Adapter` (`adapters.rs:332-452`) and `SoloMarker` (`adapters.rs:306-311`),
  so a bare instance can be passed directly to `streaming_search_with`.
- Its doc (`adapters.rs:288-294`) says it adds the Paged Results control with the supplied

### `EntryStream` iteration — what `.next()` / `.result()` do

`src/sync.rs:302-336`:

```rust
pub struct EntryStream<'a, 'b, S, A> { stream: SearchStream<'a, S, A>, conn: &'b mut LdapConn }

impl<'a,'b,S,A> EntryStream<'a,'b,S,A> where S: AsRef<str>+Send+Sync+'a, A: AsRef<[S]>+Send+Sync+'a {
    pub fn next(&mut self)  -> Result<Option<ResultEntry>>  // line 314
    pub fn result(mut self) -> LdapResult                   // line 323  (consumes self)
    pub fn last_id(&mut self) -> RequestId                  // line 333
}
```

Protocol (documented at `src/search.rs:757-759` for the async `next`, inherited by the sync
façade): you **must** call `next()` until it returns `Ok(None)` (or an `Err`), then call
`result()`. Dropping the stream early silently abandons the search and logs a warning.
`result()` consumes the stream and returns the final `LdapResult` (call `.success()` on it).

### DEFINITIVE recommendation: use the Adapter (candidate (a))

The crate ships a **synchronous example doing exactly the requested task** —
`examples/search_adapted_paged_plus_sync.rs` (declared in Cargo.toml:136-138):

```rust
use ldap3::adapters::{Adapter, EntriesOnly, PagedResults};
use ldap3::result::Result;
use ldap3::{LdapConn, Scope, SearchEntry};

fn main() -> Result<()> {
    let mut ldap = LdapConn::new("ldap://localhost:2389")?;
    let adapters: Vec<Box<dyn Adapter<_, _>>> = vec![
        Box::new(EntriesOnly::new()),
        Box::new(PagedResults::new(400)),
    ];
    let mut search = ldap.streaming_search_with(
        adapters,
        "dc=example,dc=org",
        Scope::Subtree,
        "(objectClass=*)",
        vec!["dn"],
    )?;
    while let Some(entry) = search.next()? {
        let entry = SearchEntry::construct(entry);
        println!("{:?}", entry);
    }
    let _res = search.result().success()?;
    Ok(ldap.unbind()?)
}
```

This is the idiomatic, supported pattern. The adapter loops over pages internally; you just
drain `next()`. Pair it with `EntriesOnly` (adapters.rs:208-286) so referrals/intermediate
messages are filtered out and folded into the final result instead of being yielded as
entries — without it the loop would hand you referral `ResultEntry`s. Order matters:
`EntriesOnly` first, then `PagedResults`, as in the shipped example.

The manual control loop (candidate (b)) **works** but means hand-rolling the cookie
extraction (`with_controls([PagedResults{size,cookie:vec![]}.into()])`, then on each
`LdapResult.ctrls` find `Control(Some(ControlType::PagedResults), raw)`, `raw.parse()`, feed
`pr.cookie` back). The adapter is literally a vetted implementation of that loop
(`adapters.rs:390-447`), so there is no reason to reimplement it. **Use (a).**

## 3. RESULT EXTRACTION

`EntryStream::next()` yields `Result<Option<ResultEntry>>` (`sync.rs:314`). `ResultEntry`
(`search.rs:53-55`) is the same opaque wrapper the current code already gets back from
`SearchResult.success()`. The conversion is unchanged:

`src/search.rs:148-152`:

```rust
impl SearchEntry {
    pub fn construct(re: ResultEntry) -> SearchEntry { ... }
}
```

So `SearchEntry::construct(result_entry)` **still applies** verbatim, and the resulting
`SearchEntry { dn, attrs: HashMap<String,Vec<String>>, bin_attrs: HashMap<String,Vec<Vec<u8>>> }`
(`search.rs:91-97`) feeds the worker's existing `to_ldap_entry` unchanged. With `EntriesOnly`
in the chain, every `Some(re)` handed to you is a real directory entry (referrals/intermediates
are already filtered: `adapters.rs:262-279`), so a plain
`search.next()? -> SearchEntry::construct -> to_ldap_entry` map is correct.

`ResultEntry::is_ref()` / `is_intermediate()` (`search.rs:64-71`) exist if you ever need to
classify entries yourself, but with `EntriesOnly` you don't.

## 4. ERROR / LIMIT BEHAVIOR

- **Paging avoids the per-request size limit.** RFC 2696 paging is the mechanism OpenLDAP
  uses to let a client retrieve a result set larger than `olcSizeLimit` (default 500): each
  Search PDU returns at most `page_size` entries plus a cookie; the server enforces its
  size limit per *page request*, not across the whole logical search. So a 100k-entry
  subtree comes back across ~`100000/page_size` round trips with no `sizeLimitExceeded`,
  **provided the bound identity is allowed to page** and `page_size` ≤ the server's hard
  page limit.

- **A real error still surfaces as `Err` or a non-zero `rc`.** Two surfaces:
  1. `EntryStream::next()` returns `Err(LdapError)` on a transport/protocol failure
     (e.g. `LdapError::EndOfStream` when the channel closes mid-stream, `search.rs:768-769`).
  2. `EntryStream::result()` returns the final `LdapResult` (`sync.rs:323`); call
     `.success()` on it. `LdapResult::success()` (`result.rs:63-69`) returns `Ok(self)` iff
     `rc == 0`, else `Err(LdapError::from(self))` (the non-zero result is wrapped as
     `LdapError::LdapResult { result }`, `result.rs:74-80`). The `LdapResult` carries
     `rc: u32`, `text: String`, `ctrls` (`result.rs:30-47`), so you can read the exact code.

- **Relevant LDAP result codes** (server-supplied in `LdapResult.rc`; ldap3 does not invent
  these): `sizeLimitExceeded = 4`, `timeLimitExceeded = 3`, `adminLimitExceeded = 11`.
  `adminLimitExceeded` is what OpenLDAP returns when an *administrative* cap (e.g. an unpaged
  hard limit, or `olcSizeLimit ... size.unchecked` / lookthrough limits) is hit even though
  paging is in use; `sizeLimitExceeded` is the ordinary per-search cap. Time limits surface
  the same way via `rc == 3`.

- **Detecting "server refused to page / truncated" for fallback.** Decision logic for the
  app:
  - If `streaming_search_with(...)` errors immediately, or `result().success()` returns
    `Err` with `rc ∈ {3, 4, 11}` (`timeLimitExceeded`, `sizeLimitExceeded`,
    `adminLimitExceeded`) → treat as "could not enumerate the full subtree" and fall back to
    lazy one-level browsing.
  - A server that does not support RFC 2696 ignores a non-critical control and simply returns
    one (capped) page with **no** PagedResults response control / an empty cookie; the adapter
    then ends after the first page. If you want a hard guarantee the server actually paged,
    you can mark the control critical (`MakeCritical`, `paged_results.rs:26`) so a
    non-supporting server returns `unavailableCriticalExtension (rc 12)` instead of silently
    truncating — but criticality is set on the raw control, which the adapter constructs
    itself with `crit:false`. For app purposes, the simpler robust signal is: drained fewer
    entries than expected **and** a non-zero `rc` → fall back. A clean `rc==0` finish means
    the full set was returned.

## RECOMMENDED COMPILABLE SNIPPET

"Page through an entire subtree and return `Vec<SearchEntry>`" — drop-in for the worker
(mirrors the existing `run_search` shape; uses `i32` page size as the adapter requires):

```rust
use ldap3::adapters::{Adapter, EntriesOnly, PagedResults};
use ldap3::{LdapConn, Scope, SearchEntry};
use ldap3::result::Result as LdapResultT; // ldap3's Result alias

/// Page through an entire subtree and collect every entry, bypassing the
/// server's per-request size limit via RFC 2696 Simple Paged Results.
fn search_subtree_paged(
    conn: &mut LdapConn,
    base: &str,
    filter: &str,
    attrs: Vec<String>,
    page_size: i32, // e.g. 500
) -> LdapResultT<Vec<SearchEntry>> {
    // EntriesOnly folds referrals/intermediates into the result; PagedResults
    // drives the cookie loop. Order: EntriesOnly first, then PagedResults.
    let adapters: Vec<Box<dyn Adapter<_, _>>> = vec![
        Box::new(EntriesOnly::new()),
        Box::new(PagedResults::new(page_size)),
    ];

    let mut stream = conn.streaming_search_with(
        adapters,
        base,
        Scope::Subtree,
        filter,
        attrs,
    )?;

    let mut out = Vec::new();
    while let Some(result_entry) = stream.next()? {
        out.push(SearchEntry::construct(result_entry));
    }

    // Must drain next() to None before result(); then check the final code.
    stream.result().success()?; // Err if rc != 0 (rc 3/4/11 = time/size/admin limit)

    Ok(out)
}
```

Notes for integration into `src/ldap/worker.rs`:
- `attrs: Vec<String>` satisfies `A: AsRef<[S]>` with `S = String`; matches the existing
  `run_search` parameter type.
- To convert into the worker's `LdapEntry`, chain `.map(to_ldap_entry)` over the
  `SearchEntry`s exactly as the current `run_search` does.
- For the fallback decision (Q4): inspect the `Err` from `result().success()?`; if it is
  `LdapError::LdapResult { result }` with `result.rc ∈ {3,4,11}`, switch the UI to lazy
  one-level (`Scope::OneLevel`) browsing instead of failing the whole scan.
- **Cargo.toml: no change** — `ldap3 = "0.12"` with default features already provides all of
  this.
